Архитектура импорта изображений
1. Общая схема

    Система состоит из двух процессов:

    ┌──────────────────────────────┐
    │  1. Product Import           │
    │                              │
    │  Sportfly DB                 │
    │       ↓                      │
    │  Snapshot                    │
    │       ↓                      │
    │  Products / Dependencies     │
    │       ↓                      │
    │  Fly DB                      │
    │       ↓                      │
    │  mh_images                   │
    └──────────────┬───────────────┘
                │
                │ product_import_id
                ▼
    ┌──────────────────────────────┐
    │  2. Image Transfer           │
    │                              │
    │  mh_images                   │
    │       ↓                      │
    │  ImageTransferService        │
    │       ↓                      │
    │  Sportfly filesystem         │
    │       ↓                      │
    │  Fly filesystem              │
    └──────────────────────────────┘

    Процессы раздельные, но второй зависит от результата первого.

2. Product Import

    Существующий процесс импорта товаров остаётся основным источником актуального состояния mh_images.

    Последовательность:

        SnapshotLoader
            ↓
        Snapshot
            ↓
        импорт зависимостей
            ↓
        импорт товаров
            ↓
        импорт записей изображений
            ↓
        завершение Product Import

        После успешного завершения импорта должен быть известен product_import_id

        Это идентификатор конкретного запуска импорта товаров.

            Например:
                Product Import 101

        Важно: product_import_id не является ID товара.

3. Таблица состояния переноса

    Используем одну дополнительную таблицу, например:

        __rmbt_image_transfer

    Назначение — хранить состояние последнего запуска переноса файлов.

        Минимальные поля:
            id
            product_import_id
            status
            total
            transferred
            skipped
            errors
            started_at
            finished_at
            product_import_id

        Определяет, для какого импорта товаров выполнялся перенос.

    status
        Допустимые состояния:

            pending
            running
            success
            completed_with_errors

        pending фактически можно не сохранять в БД, если процесс создаётся непосредственно перед запуском. 
            Но его можно использовать, если понадобится очередь.

    Статистика
        total
        transferred
        skipped
        errors

    Она описывает результат конкретного запуска.

4. Image Transfer

    Перенос файлов запускается отдельно от Product Import.
    Он не запускает импорт товаров и не изменяет mh_images.

    Его задача:

        прочитать актуальные mh_images
                ↓
        определить файлы
                ↓
        проверить source
                ↓
        определить target
                ↓
        перенести файл
                ↓
        сохранить результат

    Основной класс:
        Services/ImageTransferService.php
        Он отвечает непосредственно за физический перенос файлов.

5. Зависимость процессов

    Image Transfer может быть запущен только для успешно завершённого Product Import.

    Перед запуском необходимо определить:
        последний успешный product_import_id

    Затем сравнить его с:
        __rmbt_image_transfer.product_import_id
    Состояния
    Сценарий 1
        Product Import #101 Image Transfer отсутствует
        
        Результат: 🟡 Требуется перенос

    Сценарий 2
        Product Import #101  Image Transfer #101 = success

        Результат: 🟢 Изображения актуальны

    Сценарий 3
        Product Import #101 Image Transfer #101 = completed_with_errors

        Результат: 🔴 Перенос завершён с ошибками

    Сценарий 4

        После нового импорта:

            Product Import #102 Image Transfer #101 = success

        Результат: 🟡 Требуется перенос

            Потому что перенос выполнен для старой версии mh_images.

6. Интерфейс

    В интерфейсе должны быть представлены два процесса.

        Синхронизация товаров
            [ Синхронизировать ]

        Перенос изображений
            [ Перенести изображения ]

    Состояние второй операции определяется backend.

    Если перенос не выполнялся 🟡 Требуется перенос изображений
        [ Перенести изображения ]

    Если перенос успешен 🟢 Изображения актуальны
        Всего: 1250
        Перенесено: 1250
        [ Переносить изображения не нужно ]

    Если есть ошибки 🔴 Перенос завершён с ошибками
        Всего: 1250
        Перенесено: 1238
            Пропущено: 5
            Ошибок: 7
        [ Повторить перенос ]

7. Windows / Linux

    Код не должен зависеть от конкретной ОС.
    Конфигурация содержит два абсолютных filesystem root:
        source_files_root
        target_files_root

    Например локально:
        C:\...\sportfly.com.ua
        C:\...\fly.ua

    На production:
        /var/www/sportfly.com.ua
        /var/www/fly.ua

    В БД и Snapshot используются только относительные пути:
        files/products/123/image.jpg

    Фактический путь строится:
        source_files_root + relative_path
        target_files_root + relative_path

    Структура каталогов Sportfly и Fly считается одинаковой.

8. Правило копирования

    Для каждого изображения:

        1. Получить relative path.
        2. Построить source path.
        3. Построить target path.
        4. Проверить source.
        5. Создать target directory при необходимости.
        6. Проверить существование target.
        7. Если файл уже корректно существует → skipped.
        8. Если файла нет → copy.
        9. При успехе → transferred.
        10. При ошибке → errors.

    Ошибка одного файла не должна останавливать весь процесс.

9. Повторный запуск

    Процесс должен быть идемпотентным.
        То есть повторный запуск: Image Transfer #101
    не должен заново копировать уже успешно перенесённые файлы.

    Например:
        После первого запуска:
            Всего:       1250
            Уже есть:    1238
            Нужно копировать: 12

        После повторного запуска:
            transferred: 12
            skipped:     1238
            errors:      0

    Результат: success

10. Главное архитектурное разделение

    Ответственности должны быть разделены:

        ProductImporter
            ↓
        изменяет товары

        ImageImporter
            ↓
        создаёт/обновляет записи mh_images

        ImageTransferService
            ↓
        переносит физические файлы

        UI / Controller
            ↓
        запускает процессы и показывает состояние

    При этом:
        ImageTransferService не должен заниматься БД-импортом изображений.

    И наоборот:
        ImageImporter не должен заниматься физическим копированием файлов.

11. Итоговая зависимость

    Вся система сводится к одному правилу:

        Product Import #N
            ↓
        актуальная mh_images
            ↓
        Image Transfer #N
            ↓
        актуальная файловая система

    Если появился:

        Product Import #N+1

    то предыдущий перенос автоматически становится неактуальным, пока не выполнен:

        Image Transfer #N+1

    Это даёт нам простую, проверяемую и расширяемую архитектуру 
        без лишнего количества таблиц и 
        без смешивания ответственности 
        между импортом БД и файловым переносом.
